How to Conduct Secure Online Exams Without Cheating: Best Practices & Tools

No platform can promise that cheating is impossible. A secure online exam system for schools reduces opportunity, records relevant signals and gives trained staff a fair process for reviewing exceptions.

Start with the right security model

“Online exams without cheating” is an understandable goal but an unsafe promise. A student may have another device, receive help outside the camera view or encounter a genuine technical event that resembles suspicious behaviour. Browser controls can deter common actions and monitoring can produce signals, but neither proves intent by itself. The school's objective should be a defensible assessment: appropriate controls, reliable records, human review, accessible alternatives and a published process for handling incidents.

Think in layers. The first layer is assessment design, followed by authenticated access, controlled timing, question variation, browser signals, optional proctoring, secure submission and a review process. Each layer reduces a different risk. No single layer should carry the whole decision, and a software flag should never automatically become an accusation.

Design an assessment that is harder to outsource

Security begins before a student signs in. Questions that require explanation, comparison, working steps or application to a fresh scenario are harder to answer by copying a line from a textbook. A balanced paper can combine automatically scored questions with short responses or follow-up discussion where the learning objective requires it. Use age-appropriate language and make the mark scheme clear enough that different teachers would judge the same answer consistently.

Create enough questions to avoid reusing an identical sequence across sections. Tag questions by subject, chapter, outcome, difficulty and marks. Review distractors in multiple-choice questions so that wrong options are plausible without being misleading. Remove accidental clues such as one answer being much longer than the others. Have another teacher attempt the paper and record completion time before setting the final limit.

Open-book assessment can sometimes be more secure than pretending students have no access to resources. If the learning objective is interpretation or problem solving, allow named materials and ask questions that require using them. State what collaboration and tools are permitted. Clear rules reduce both misconduct and false allegations.

Use randomisation without damaging fairness

A question bank can supply different but equivalent selections to students, while question-order and option-order shuffling makes simple screen sharing less useful. These controls are not interchangeable. Random selection requires a sufficiently large, tagged and quality-checked bank. Shuffling changes presentation but not which concepts are assessed. If one student receives mostly difficult items and another receives mostly easy ones, randomness has weakened validity.

Build blueprints that specify how many questions come from each topic and difficulty level. Keep marks and expected time comparable. For calculation questions, use parameter variations only when every generated value produces a valid problem and a checked answer. Preview several forms as a teacher. Preserve the exact order and content served to each attempt so results can be reviewed later.

Do not reveal correct answers while other students can still take the examination. Decide whether students see only a submission receipt, a score, or full answer review, and schedule release accordingly. Restrict editing after publication; if a question must be corrected, document the change and apply a consistent scoring decision.

Control identity, eligibility and attempts

Require each student to use an individual authenticated account. Avoid public links or credentials shared by a whole class. Enrolment and class assignment should determine eligibility so a student sees only the correct tests. Protect staff publishing and review roles separately, and use stronger authentication for administrators where available.

Define the attempt policy before launch: opening and closing time, duration, grace period, whether late starts are allowed, what happens when time expires and who may authorise another attempt. A one-attempt rule is simple but needs an exception process for power, device or connectivity failure. Store when the attempt started, when answers were saved, how it ended and who approved any reset. An exception without an audit trail can look like favouritism even when it was justified.

Autosave answers or save on each change so a brief interruption does not erase work. The server—not only the student's device—should enforce timing and submission state. Reopening a browser should return to the same authorised attempt and stable question order, not create a fresh paper.

Understand what browser lockdown can and cannot do

A standard web application can request fullscreen, detect when its tab or window loses visibility, block copying and pasting inside the page, and disable a context menu. It cannot control every device, application or network activity like a dedicated managed-device environment. A student can leave fullscreen accidentally, receive an operating-system notification or lose focus because of assistive technology. Treat these events as reviewable signals.

Publish the controls in advance and run a practice test on the same device types students will use. Explain which actions are blocked, which events are logged, when an attempt may auto-submit and how to report a technical problem. Avoid introducing a new lockdown requirement during a high-stakes examination. If the school uses a dedicated secure browser or device-management policy, test updates, keyboard accessibility, permitted calculators and network filtering well before exam day.

Set thresholds cautiously. One tab-blur event should not equal misconduct. Repeated events in a short period may justify review, but context matters. Preserve event times beside saved answers and connection events. The purpose is to help a teacher reconstruct what happened, not to let a counter decide the student's intent.

Use webcam and AI proctoring proportionately

Webcam monitoring is intrusive and should be used only when the assessment risk justifies it. A school needs a documented purpose, appropriate guardian or institutional consent, clear notice, limited access and a retention schedule. Offer a reasonable alternative where consent, disability, device availability, home circumstances or policy requires one.

Periodic still images generally collect less data than continuous video, but they still contain personal information and the student's surroundings. Store them outside public upload paths, encrypt transport, restrict reviewer roles and log staff access. Delete them according to the disclosed schedule unless an incident requires an authorised hold. Do not reuse them for unrelated identification or training.

On-device face-presence detection can flag that no face or more than one face appears without performing identity recognition. Even then, lighting, camera angle, movement, skin-tone performance differences, disability and another family member entering the room can create errors. AI output is a prompt to review, not a verdict. A teacher should consider the full timeline, assessment pattern and student explanation before any decision.

Protect privacy, accessibility and dignity

Collect the minimum data needed for the stated exam purpose. Tell students and guardians what is captured, why, who can see it, how long it remains and how to raise a concern. Separate consent for optional proctoring from general portal access. A student should not be able to grant guardian consent on their own, and a school-side grant should identify the authorised person and basis.

Review the exam for keyboard access, readable contrast, screen-reader labels, zoom, additional-time accommodations and permitted assistive tools. Lockdown controls must not block the technology a student needs. Apply approved accommodations without exposing them to classmates. Test low-bandwidth behaviour, mobile limitations and power-loss recovery. Security that prevents an eligible student from demonstrating learning is not a successful control.

Limit result visibility as carefully as proctoring data. Students should see their own attempt; teachers should see only assigned or authorised groups; parents should see linked children where school policy permits. Avoid publishing class rank or identifiable incident details broadly. Exported reports and downloaded images need the same handling rules as records inside the system.

Run a secure exam as an operational process

Seven days before the test, freeze the blueprint, verify every question and run a full practice attempt. Check start and end times, time zone, duration, eligible students, scoring, shuffling, result-release settings, proctoring policy and accommodations. Confirm that support staff know who can reset an attempt and what evidence is required. Take a backup or export appropriate to the platform and record the version being used.

On exam day, open a support channel that does not disclose answers. Monitor platform health and record broad outages separately from individual incidents. Tell students to report a failure immediately with the time and visible error. Do not ask them to send passwords or sensitive screenshots through informal messaging. If a wide outage occurs, pause or reschedule consistently rather than making individual improvised promises.

After submission, reconcile the number of eligible students, started attempts, submitted attempts, timed-out attempts and authorised absences. Review technical failures before suspicious-event queues. Release scores only after teachers have handled invalid questions and approved exceptions. Keep a short decision log so the same kind of incident receives the same treatment across sections.

Review incidents fairly and consistently

Create an incident rubric before the exam. It should distinguish a technical event, an unexplained pattern, corroborated misconduct and an inconclusive case. Define who reviews, what evidence is considered, how the student can respond, who decides and how an appeal works. Avoid language that assumes guilt before review.

Look at the whole record: browser events, answer-save timing, network interruptions, question order, webcam snapshots where lawfully collected, invigilator notes and the student's explanation. Similar answers between students can have innocent causes, especially for short factual questions. Automated similarity or face-presence flags require human interpretation. Record the evidence supporting the decision and restrict access to those with a legitimate role.

Use incident trends to improve the next assessment. Many fullscreen exits may indicate unclear device instructions. Many students timing out on one question may show a flawed item. Repeated connection failures may require smaller assets or a different schedule. Security review should improve design and operations, not only assign penalties.

Where Schoolment fits

Schoolment's Online Exam module requires portal login, supports timed one-attempt quizzes with automatically gradable question types, saves attempt records and can shuffle question and option order per attempt. Teachers can publish tests to selected classes and review results in the same school platform.

The optional proctoring add-on can require fullscreen and record tab or window changes, copy or paste attempts and related browser events. A policy can enable periodic webcam snapshots and on-device face-presence flags. Guardian or authorised school consent is required before a proctored attempt. Events and snapshots are presented for authorised human review; they are not automatic proof of cheating.

Schoolment does not make cheating impossible and should not be described that way. Its role is to combine assessment records, deterrent controls, consent, evidence and review inside a defined workflow. Schools remain responsible for their examination policy, accommodations, legal obligations and final academic decisions.

Secure online exam final checklist

  • The assessment blueprint and every question have been peer reviewed.
  • Eligible students, timing, time zone, duration and accommodations are correct.
  • Question selection or shuffling produces fair and stable attempts.
  • Authentication, attempt limits, autosave and timeout submission were tested.
  • Students completed a practice run on representative devices and connections.
  • Browser and proctoring controls are disclosed, proportionate and consented where required.
  • Monitoring data has restricted access, an access record and a retention schedule.
  • A technical-failure and authorised-reattempt process is ready.
  • Flags lead to human review under a published incident rubric.
  • Result release waits for scoring checks, exception review and approval.

A secure examination is not one setting. It is a chain of decisions that protects validity, privacy and fairness from paper design through final result release.

Keep a one-page exam record after completion: the approved blueprint, published instructions, configuration summary, eligible-student count, participation totals, technical incidents, authorised retries, invalid-question decisions and result-release approval. Review it with the academic coordinator while events are still fresh. This small record gives the school evidence that controls were applied consistently and turns each examination into a better starting point for the next one. It also helps distinguish a platform problem from an assessment-design problem when teachers evaluate the results.

Share the resulting improvements with students before the next test. Transparent rules and visible corrections build more trust than increasingly severe controls introduced without explanation.
