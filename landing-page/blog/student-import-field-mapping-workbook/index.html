Student Imports: Agree the Field Mapping Before Uploading a Spreadsheet

Prepare a source-to-target mapping for student identifiers, names, contacts and class values before migration.

Introduction

A spreadsheet column can look familiar while meaning something different in the destination system. “Class” might contain a grade, a grade and section together, or a previous-year placement. “Parent” might identify a contact person without establishing the relationship or access that person should receive. A field mapping workbook makes those differences explicit before an import turns them into operational errors.

The workbook connects each source value to its intended destination, explains approved transformations and identifies information that requires a human decision. It is not simply a list of matching column names. A useful mapping records meaning, format, ownership and the treatment of exceptions so another reviewer can understand how the resulting records were produced.

This guide describes a proposed administrative process for a school migration or controlled bulk upload. Its examples are fictional. Use the actual import specification supplied for your configured system, and keep technical execution with the authorised implementation team. Do not use these examples as permission to change live records without the school's normal review.

Describe the source before choosing destination fields

Identify the file's origin, academic period and responsible owner. A spreadsheet maintained by reception may describe application enquiries, while an academic register describes enrolled students. Even when both contain names and class labels, their populations and meanings differ. Record those distinctions before treating one as a master source.

Keep the accepted source version separate from cleaned working copies. Note when it was produced and which filters or exclusions apply. If the office continues updating the source during preparation, agree on how later changes will be captured. The mapping should not silently shift between yesterday's file and today's revised list.

Ask the source owner to explain unclear columns. A short abbreviation can have a local meaning that is not evident to the migration team. Record that explanation in ordinary language, then confirm whether the destination has a field with the same meaning. Similar labels alone are not sufficient evidence of a correct match.

Create one mapping row for each destination decision

A practical workbook identifies the source column, destination field, meaning, required representation and transformation rule. Include whether the destination requires a value and who can decide what happens when the source is blank or inconsistent. A notes column can hold the reason for a non-obvious decision.

Some destination fields may draw from several source columns, and some source columns may split into several destinations. Record those relationships explicitly rather than squeezing them into a misleading one-to-one list. For example, a combined grade-section value may require separate approved grade and section mappings.

Do not hide a policy decision inside a technical formula. Choosing a current academic year, interpreting an enrolment status or deciding which contact becomes the primary recipient can affect how the school operates. Such decisions need the relevant school owner, even if the eventual transformation is simple to implement. The workbook should show who approved the interpretation.

Preserve identifiers as references, not calculations

Identify the source references used to distinguish students, applications and contacts. Treat those values according to their purpose rather than their appearance. An admission reference containing digits is still an identifier; it is not an amount to add or a measurement to round.

Include examples with leading zeros, letters or punctuation where these occur in the actual approved source. Verify that the transformation and receiving process preserve the intended representation. If a value changes when a spreadsheet is opened, investigate the handling of the file before assuming that the source record itself changed.

Avoid matching people by name alone. Names may repeat or be corrected, while siblings may share contact details. The implementation team should explain the supported identification and matching process. Where a reliable link is missing, record the exception for review instead of inventing an identifier that appears valid but cannot be traced to an authorised source.

Map class and section values with an explicit crosswalk

List the source values used for classes and sections, then connect each to the destination's approved values. A source entry such as “VI-B” might map to Class 6 and Section B. Another entry such as “6 B” may have the same intended meaning, but the school should confirm that interpretation rather than relying on a guess.

Keep ambiguous values out of the automatic transformation. A row containing only “6” may be missing a section, or the relevant school process may not use sections. The correct treatment depends on the approved destination configuration and the meaning of the source, not on what would make the upload succeed fastest.

Check the academic year associated with placement. A student identity can remain the same while class membership changes. Mapping a previous-year class into the current-year field can produce a plausible-looking but incorrect roster. The workbook should state which year's placement is being imported and which team has verified it.

Distinguish dates by the event they represent

Several dates can appear in a student file: application, admission, joining, record creation and withdrawal dates may all answer different questions. Write the event meaning beside the mapping. A destination field should not receive a conveniently available date merely because the intended date is missing.

Use the destination's documented date representation and confirm how ambiguous source values are interpreted. If a source format can be read in more than one way, refer it to the owner rather than choosing an interpretation silently. Keep original values available in the controlled review evidence so the decision can be traced.

Consider missing dates separately from invalid ones. A blank may mean that an event has not occurred, that the information was not collected or that the source is incomplete. Those situations may require different treatment. The mapping workbook should record the approved rule and the cases that remain exceptions, instead of filling every empty cell with today's date.

Define blank, unknown and not-applicable treatments

Blank values are easy to overlook because they contain no visible text, but they often carry important uncertainty. Ask the source owner what a blank means for each relevant field. Do not assume that all empty cells represent the same situation.

Where the destination supports a meaningful absence, use the documented representation. Where it requires a value, identify the authorised decision needed. Invented phone numbers, placeholder dates and guessed categories can make an import pass while creating future operational problems. A rejected row with an owner is preferable to a false value that later staff mistake for verified information.

Keep default values limited to cases where the default is genuinely approved and appropriate to the whole affected population. Document the basis for that choice. If a default applies only to one source group, make the condition explicit so it does not spread to unrelated records during a later rerun or reuse of the workbook.

Treat family relationships as their own mapping problem

A contact name and phone number do not, by themselves, describe every relationship the destination may need. Identify which source fields establish the authorised contact relationship and how the system represents links between students and family accounts. Keep identity, communication preference and access decisions distinguishable.

Review siblings and multiple-contact cases in the sample. The same contact may legitimately relate to more than one student, while similar contact details do not automatically establish the same family relationship. The authorised school reviewer should resolve uncertain links using the normal process.

Do not grant portal access merely because a contact appeared in a general spreadsheet. Confirm the approval and configuration required for the receiving workflow. A migration mapping is a record transformation, not a substitute for the school's decision about who may see a student's information. Record that boundary so technical convenience does not determine access.

Separate cleaning from changing the underlying facts

Cleaning can include applying an approved representation consistently, but it should not become an opportunity to rewrite uncertain facts. Removing accidental surrounding spaces is different from deciding that two differently spelled names refer to the same person. The workbook should distinguish straightforward formatting rules from decisions requiring review.

Keep transformations understandable. A reviewer should be able to explain what a rule does to a representative value and why. Avoid a chain of undocumented changes that produces a tidy file but leaves nobody able to reconstruct how a particular record was altered.

Where a source fact is wrong, use the authorised correction process and record the decision. Then apply the corrected source or an explicitly approved transformation. Do not describe a factual correction as mere formatting, because that hides responsibility for the changed information. The resulting student record should have a defensible connection to the evidence the school accepted.

Worked example: a mixed class column

Consider a fictional file with Class values “VI-B”, “6 B”, “Class 6 / B” and “6”. The academic owner confirms that the first three describe the same current-year placement. The mapping crosswalk connects them to the destination's approved Class 6 and Section B values.

The fourth value remains unresolved because it does not establish the section. The migration team does not copy Section B from neighbouring rows or infer it from the student's surname. The exception is assigned to the academic owner, who checks the authorised class allocation and records the answer.

The workbook now contains both the normalisation rule and the exception treatment. A sample import includes all four source patterns. The reviewer checks the resulting placement for each accepted record, then confirms that the unresolved case is handled as agreed. This tests the actual meaning of the mapping rather than only whether the spreadsheet has the right number of columns.

Choose a sample that tests decisions, not just easy rows

A useful sample includes ordinary records and cases that exercise the mapping rules. Select examples with missing optional values, different class representations, multiple contacts and the source statuses relevant to the migration. Use authorised records or fictional examples appropriate to the testing environment.

Keep a list of the expected destination outcomes for each sample. Without that reference, reviewers can be impressed by a successful upload while overlooking an incorrect field interpretation. The expected result should include relationships and status meaning, not just whether a name appears.

Check rejected cases as carefully as accepted ones. A row intended to be held for review should not slip through with an invented default. Conversely, a valid source pattern should not be rejected merely because the transformation omitted an approved variant. The sample is a test of both the normal route and the exception rules.

Record import findings against the mapping rule

When a sample produces an unexpected result, identify which mapping decision is involved. The cause may be an incorrect source interpretation, an unsupported destination value or an error in applying an otherwise correct rule. Keep those possibilities separate until the evidence establishes the cause.

Update the workbook through a controlled review rather than changing only the working spreadsheet. Otherwise the next run may recreate the same issue because the documented rule no longer matches the actual correction. Record the changed rule, its approval and the sample cases that must be tested again.

Avoid broad fixes based on one record without checking the affected population. A rule that solves one class label may damage another valid pattern. Ask which other source values use the same transformation and include those in the retest. The aim is a reliable mapping across the agreed scope, not a series of isolated patches to individual rows.

Approve the mapping before the full run

The relevant school owners should review the decisions that affect their work before the final import. Academic staff may approve class and year interpretation, administrators may confirm student identity fields, and the appropriate contact owner may review family relationships. Technical staff confirm that the documented rules can be applied through the supported process.

The approval should identify the source version, mapping version and unresolved exceptions. A general statement that “the file is ready” is less useful than a clear record of what was checked and which cases are deliberately outside the run.

Do not treat approval as permission to ignore later discrepancies. It establishes the agreed basis for execution. If the full run reveals a source pattern not covered by the mapping, stop that case for review through the exception route rather than extending the rule informally. A controlled process remains responsive without becoming arbitrary.

Reconcile the full import without losing the mapping evidence

After the full run, compare the expected population with accepted, rejected and intentionally excluded records using the agreed count definitions. Keep those totals linked to the mapping version used. Counts help identify unexplained gaps, while field-level review checks whether accepted records carry the intended meaning.

Verify a representative set in the destination after processing, including the more complicated cases tested earlier. Confirm that the operational team can recognise the intended identity, placement and relationships. A processing summary alone does not establish that staff can use the records correctly.

Keep the mapping workbook, source reference and review outcomes together through the approved storage process. If someone later asks why a value changed, the school should be able to trace the decision rather than searching through private messages. The workbook remains useful after migration because it explains the destination's starting information.

Maintain the workbook when another upload is needed

A later upload should not automatically reuse an old mapping without review. The source may have changed its columns, the destination may use a revised configuration or the school may now be importing a different academic period. Confirm that the original assumptions still apply.

Create a distinguishable version for material changes and repeat the relevant sample tests. Keep the earlier version available according to the school's document process so previous imports remain explainable. Avoid editing history in a way that makes an older run appear to have used rules that did not exist at the time.

For a Schoolment implementation, ask the delivery team to demonstrate the actual supported import specification and work through this mapping review with the responsible school owners. The best workbook is not the one with the most technical notation. It is the one that lets the school explain where each important value came from, how it was interpreted and what happened when the answer was uncertain.
